Hands-on kernel lab

CUDA kernel engineering from bandwidth to vector search.

This repository is a compact, reproducible CUDA engineering lab. It starts with a memory-bound vector operation, introduces hierarchical reduction, and applies both ideas to exact L2 vector search. Every executable includes a CPU reference or bounded correctness check and reports GPU timing separately from setup work.

First target

Understand launch configuration, grid-stride loops, and memory transfer cost.

Second target

Learn reductions using warp shuffles and block-level aggregation.

Third target

Build an exact L2 search baseline before moving to ANN-style algorithms.

Execution Flow

All three executables follow the same host/device lifecycle. Keeping these stages explicit makes it possible to separate correctness, kernel throughput, transfer cost, and final CPU work.

  1. Prepare on CPUAllocate host vectors, generate deterministic inputs, and compute or reserve a CPU reference.
  2. Transfer to GPUAllocate device buffers and copy the required inputs from host memory.
  3. Warm up & executeLaunch once for validation, synchronize, then repeat the kernel inside CUDA-event timing.
  4. Copy results backTransfer the output or partial results required for host-side validation and selection.
  5. Validate & reportCompare with the CPU result, report numerical error, kernel time, and derived throughput.
Why this flow: it is intentionally transparent and easy to audit. A production pipeline would overlap transfers and kernels, reuse allocations, batch queries, and keep final selection on the GPU—but those optimizations make the baseline harder to reason about.

Design Decisions & Alternatives

There is no universally best CUDA implementation. The selected option is the best fit for the current learning objective; the production recommendation changes when scale, latency, or maintainability becomes the priority.

DecisionAvailable choicesCurrent choice and reasonBetter production direction
Element traversal 3 choices: one thread per element; grid-stride loop; vectorized loads Grid-stride loop — handles arrays larger than the launch and keeps launch size tunable. Add aligned float4 loads only after profiling confirms instruction or transaction overhead.
Reduction 4 choices: global atomics; shared-memory tree; warp shuffle; CUB Warp shuffle + block partials — exposes warp and block cooperation without global atomic contention. cub::DeviceReduce is the maintained baseline; use custom code only with measured evidence.
L2 work mapping 3 choices: thread per vector; block per vector; tiled/batched matrix formulation Block per vector — threads cooperate across 128 dimensions and reduce one distance clearly. Batched/tiled search improves data reuse; compare with cuVS brute force before custom tuning.
Top-k selection 4 choices: full CPU sort; CPU partial selection; GPU selection; library index CPU partial selection — simple correctness baseline after GPU distance generation. GPU top-k avoids transferring every distance; cuVS/Faiss is preferable for production search.
Timing scope 3 choices: kernel-only events; end-to-end wall time; profiler-derived metrics Kernel-only CUDA events — isolates kernel behavior for the first controlled comparison. Report kernel and end-to-end distributions together, then explain the gap with Nsight Systems.

Modernization Roadmap

The current kernels are a useful foundation, but a modern performance portfolio needs library baselines, reproducible measurements, asynchronous execution, and a complete GPU search path. The work below is ordered by value and by what can be measured honestly on the available RTX 4080 Super (sm_89).

Complete the exact vector-search pipeline

Add batched queries, cosine similarity, inner product, FP16 storage with FP32 accumulation, vectorized loads, shared-memory query caching, and GPU-side top-k. Report recall/correctness against the CPU implementation as well as kernel-only and end-to-end latency.

Compare with cuVS

Benchmark the custom exact search against cuVS brute force, then add CAGRA, IVF-Flat, and IVF-PQ comparisons. Record recall@k, p50/p95 latency, throughput, index-build time, and memory use instead of presenting throughput alone.

Asynchronous execution and reusable memory

Add pinned host buffers, cudaMemcpyAsync, multiple streams, double buffering, cudaMallocAsync/cudaFreeAsync, and CUDA Graph capture for repeated batches. Measure when launch, allocation, and transfer overhead dominate short kernels.

Reproducible benchmark engineering

Introduce CMake, automatic architecture detection, warmups, repeated trials, median/p50/p95/standard deviation, JSON or CSV output, and a script that regenerates the website tables. Record the GPU, driver, toolkit, compiler, clocks, build flags, and git commit beside every result.

Optional advanced track: explore CUTLASS 4 and CuTe DSL for tiled GEMM, mixed precision, and fused operators. CUTLASS 4.6 includes CUDA-native DSL tooling, but NVIDIA currently documents Windows limitations, so use Linux or WSL for this track. CUTLASS overview

TMA starts at compute capability 9.0; the RTX 4080 Super is 8.9. These topics can be documented or compile-tested separately until compatible hardware is available.

CUDA Mental Model

Grid, Block, Thread

A kernel launch creates a grid of thread blocks. Each block contains threads. Your code maps each thread to one or more data elements using built-in IDs such as blockIdx.x, blockDim.x, and threadIdx.x.

Official reference: CUDA C++ Programming Guide.

Warp

A warp is the hardware execution group of 32 threads. Many performance questions become clearer when you ask: "What are the 32 neighboring threads in this warp doing?"

Practice this in the reduction example with __shfl_down_sync.

Global Memory

Global memory is large but high-latency. Kernel speed often depends on whether neighboring threads read neighboring addresses so hardware can coalesce memory transactions efficiently.

Read: Unlock GPU Performance: Global Memory Access in CUDA.

Shared Memory

Shared memory is block-local, programmer-managed memory. It is useful when threads in one block reuse data or need to cooperate, but it adds synchronization and bank conflict concerns.

Read: Using Shared Memory in CUDA C/C++.

Grid-Stride Loops

A grid-stride loop lets each thread process multiple elements: for (int i = tid; i < n; i += blockDim.x * gridDim.x). This makes kernels scalable and easier to debug.

Read: CUDA Pro Tip: Grid-Stride Loops.

Occupancy

Occupancy is about how many warps can be active on an SM. Higher occupancy can help hide latency, but it is not automatically equal to higher performance. Registers, shared memory, and block size all matter.

Read: CUDA C++ Best Practices Guide.

Practice Modules

01: Vector Add

thread indexing grid-stride loop memory bandwidth

File: src/01_vector_add.cu. This is the "hello, GPU memory" exercise. It reads two arrays and writes one array, so the bandwidth model is roughly 3 * n * sizeof(float) bytes per iteration. 

__global__ void vectorAddKernel(const float* a, const float* b, float* c, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = tid; i < n; i += stride) {
        c[i] = a[i] + b[i];
    }
}

What to learn: thread ID math, launch configuration, correctness checks, and event timing.

Modify: try block sizes 128, 256, 512, and 1024.

02: Dot Product Reduction

warp shuffle block reduction floating-point error

File: src/02_dot_product_reduction.cu. This kernel computes partial dot-product sums on the GPU and finishes the final accumulation on CPU. That two-stage pattern appears constantly in high-performance kernels. 

__inline__ __device__ float warpReduceSum(float value)
{
    for (int offset = warpSize / 2; offset > 0; offset /= 2) {
        value += __shfl_down_sync(0xffffffff, value, offset);
    }
    return value;
}

What to learn: reductions, warp-level communication, partial sums, and numerical drift.

Modify: compare this approach with a naive global atomicAdd.

03: Exact L2 Distance Search

vector search L2 distance top-k baseline

File: src/03_l2_distance_search.cu. This is the first bridge from CUDA practice to vector database engineering. One CUDA block computes the distance from the query vector to one database vector, then CPU code selects the top-k nearest results. 

for (int d = threadIdx.x; d < dim; d += blockDim.x) {
    float diff = vector[d] - query[d];
    sum += diff * diff;
}

What to learn: exact kNN baseline, distance kernels, bandwidth limits, and top-k design.

Modify: change dimensions to 256, 512, and 768.

The first two bars share a 0–700 GB/s visual scale. L2 uses a separate 0–1,000M comparisons/s scale; its bar communicates magnitude within that metric, not superiority over bandwidth.

What is measured

  • A correctness launch and device synchronization occur before timing.
  • CUDA events measure repeated kernel launches on the default stream.
  • Vector add and L2 search average 50 iterations; dot product averages 100 iterations.
  • Reported bandwidth is derived from known bytes read and written.

What is excluded

  • Host allocation and input generation.
  • Device allocation and host/device transfers.
  • Final CPU accumulation or top-k selection.
  • Variance, percentiles, power, temperature, and clock stability.
Interpretation: the table answers “how fast is the isolated kernel for this fixed workload after setup?” It does not answer “how fast is the complete application?” Future benchmark output should include median, p50/p95, standard deviation, end-to-end latency, device clocks, driver version, compiler flags, and the exact git commit.

Experiments

Block-size sweep

Test 128, 256, 512, and 1024 threads per block. Record kernel time and bandwidth. Ask whether the result changed because of occupancy, memory behavior, or reduction overhead.

Problem-size sweep

For vector add and dot product, test 1<<20, 1<<24, and 1<<26. Small workloads may underutilize the GPU; large workloads show steadier bandwidth.

Dimension sweep for L2 search

Test vector dimensions 128, 256, 512, and 768. This connects directly to embedding workloads such as RAG.

Top-k on GPU

Current L2 search computes distances on GPU but selects top-k on CPU. The next kernel should keep candidate selection on GPU to reduce transfer and improve end-to-end latency.

Batched queries

Process multiple queries at once. GPU vector search often improves with batching because there is more parallel work and better amortization of memory movement.

Profiling & Debugging

Timing With CUDA Events

CUDA events measure elapsed GPU time between recorded events. This is appropriate for kernel timing, but it does not automatically include CPU work or memory allocation.

Reference: CUDA Runtime API event management.

Nsight Compute

Use Nsight Compute when you want kernel-level metrics: memory throughput, occupancy, warp stalls, branch behavior, and instruction mix. 

ncu --set basic .\build\01_vector_add.exe
ncu --set basic .\build\03_l2_distance_search.exe

Reference: Nsight Compute documentation.

Nsight Systems

Use Nsight Systems for whole-application timelines: CPU activity, CUDA API calls, kernel launches, copies, and overlap between compute and transfer.

Reference: Nsight Systems User Guide.

Compute Sanitizer

Use Compute Sanitizer to catch invalid memory access, race conditions, and sync bugs. It is slower than normal execution, but it is a wonderful bug net. 

compute-sanitizer .\build\01_vector_add.exe
compute-sanitizer --tool racecheck .\build\02_dot_product_reduction.exe

Reference: Compute Sanitizer documentation.

A practical optimization loop: verify correctness, measure baseline, profile bottleneck, change one thing, remeasure, document result. Small disciplined loops beat heroic guessing.

Vector Search Path

The current L2 kernel is an exact brute-force baseline. That baseline matters because ANN systems are only meaningful when you know what exact results and exact costs look like.

Exact Search

Computes distance from query to every vector. Simple, accurate, bandwidth-heavy. In Faiss vocabulary, this is like IndexFlatL2.

Read: Faiss guidelines to choose an index.

ANN Search

Avoids checking every vector. IVF clusters the search space, PQ compresses vectors, and graph methods like HNSW/CAGRA traverse neighbor graphs.

Read: NVIDIA cuVS documentation.

GPU Vector Search

GPU search depends heavily on batching, memory layout, candidate expansion, and keeping enough work on-device to amortize transfers.

Read: Fine-tuning GPU index algorithms.

Production Libraries

Study cuVS and Faiss after your baseline works. Then you can compare your code against real systems with humility and sharper eyes.

Repos: cuVS, Faiss, ANN-Benchmarks.

Engineering Assessment

The project demonstrates a sound optimization workflow: define a CPU reference, validate the GPU result, isolate a baseline measurement, identify the dominant resource, change one design variable, and remeasure. Its strongest result is not a single throughput number; it is the traceable progression from a memory-bound primitive to a reduction and then to an exact-search workload with explicit limitations.

Demonstrated

  • Grid-stride indexing and coalesced contiguous access.
  • Warp-shuffle and block-level reduction.
  • CUDA-event timing and derived throughput.
  • CPU/GPU correctness comparison and floating-point error reporting.
  • An exact L2 baseline connected to vector-search terminology.

Not yet demonstrated

  • Nsight Compute evidence for the stated bottlenecks.
  • CUB, Thrust, cuBLAS, Faiss, or cuVS comparisons.
  • Batched queries, GPU top-k, asynchronous pipelines, or CUDA Graphs.
  • Portable CMake builds and automated regression tests.
  • Real embedding datasets and recall/latency evaluation.
