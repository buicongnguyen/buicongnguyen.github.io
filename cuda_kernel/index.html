Hands-on kernel lab

Practice CUDA kernels by building toward vector search.

This guide turns the cuda_kernel repo into a structured training path: start with memory bandwidth, learn reductions, then move into exact L2 vector search. That sequence is intentionally chosen because vector databases and accelerator libraries are built from the same primitives: move data efficiently, compute distances, reduce or select top candidates, and measure everything honestly.

First target

Understand launch configuration, grid-stride loops, and memory transfer cost.

Second target

Learn reductions using warp shuffles and block-level aggregation.

Third target

Build an exact L2 search baseline before moving to ANN-style algorithms.

CUDA Mental Model

Grid, Block, Thread

A kernel launch creates a grid of thread blocks. Each block contains threads. Your code maps each thread to one or more data elements using built-in IDs such as blockIdx.x, blockDim.x, and threadIdx.x.

Official reference: CUDA C++ Programming Guide.

Warp

A warp is the hardware execution group of 32 threads. Many performance questions become clearer when you ask: "What are the 32 neighboring threads in this warp doing?"

Practice this in the reduction example with __shfl_down_sync.

Global Memory

Global memory is large but high-latency. Kernel speed often depends on whether neighboring threads read neighboring addresses so hardware can coalesce memory transactions efficiently.

Read: Unlock GPU Performance: Global Memory Access in CUDA.

Shared Memory

Shared memory is block-local, programmer-managed memory. It is useful when threads in one block reuse data or need to cooperate, but it adds synchronization and bank conflict concerns.

Read: Using Shared Memory in CUDA C/C++.

Grid-Stride Loops

A grid-stride loop lets each thread process multiple elements: for (int i = tid; i < n; i += blockDim.x * gridDim.x). This makes kernels scalable and easier to debug.

Read: CUDA Pro Tip: Grid-Stride Loops.

Occupancy

Occupancy is about how many warps can be active on an SM. Higher occupancy can help hide latency, but it is not automatically equal to higher performance. Registers, shared memory, and block size all matter.

Read: CUDA C++ Best Practices Guide.

Practice Modules

01: Vector Add

thread indexing grid-stride loop memory bandwidth

File: src/01_vector_add.cu. This is the "hello, GPU memory" exercise. It reads two arrays and writes one array, so the bandwidth model is roughly 3 * n * sizeof(float) bytes per iteration. 

__global__ void vectorAddKernel(const float* a, const float* b, float* c, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = tid; i < n; i += stride) {
        c[i] = a[i] + b[i];
    }
}

What to learn: thread ID math, launch configuration, correctness checks, and event timing.

Modify: try block sizes 128, 256, 512, and 1024.

02: Dot Product Reduction

warp shuffle block reduction floating-point error

File: src/02_dot_product_reduction.cu. This kernel computes partial dot-product sums on the GPU and finishes the final accumulation on CPU. That two-stage pattern appears constantly in high-performance kernels. 

__inline__ __device__ float warpReduceSum(float value)
{
    for (int offset = warpSize / 2; offset > 0; offset /= 2) {
        value += __shfl_down_sync(0xffffffff, value, offset);
    }
    return value;
}

What to learn: reductions, warp-level communication, partial sums, and numerical drift.

Modify: compare this approach with a naive global atomicAdd.

03: Exact L2 Distance Search

vector search L2 distance top-k baseline

File: src/03_l2_distance_search.cu. This is the first bridge from CUDA practice to vector database engineering. One CUDA block computes the distance from the query vector to one database vector, then CPU code selects the top-k nearest results. 

for (int d = threadIdx.x; d < dim; d += blockDim.x) {
    float diff = vector[d] - query[d];
    sum += diff * diff;
}

What to learn: exact kNN baseline, distance kernels, bandwidth limits, and top-k design.

Modify: change dimensions to 256, 512, and 768.

Experiments

Block-size sweep

Test 128, 256, 512, and 1024 threads per block. Record kernel time and bandwidth. Ask whether the result changed because of occupancy, memory behavior, or reduction overhead.

Problem-size sweep

For vector add and dot product, test 1<<20, 1<<24, and 1<<26. Small workloads may underutilize the GPU; large workloads show steadier bandwidth.

Dimension sweep for L2 search

Test vector dimensions 128, 256, 512, and 768. This connects directly to embedding workloads such as RAG.

Top-k on GPU

Current L2 search computes distances on GPU but selects top-k on CPU. The next kernel should keep candidate selection on GPU to reduce transfer and improve end-to-end latency.

Batched queries

Process multiple queries at once. GPU vector search often improves with batching because there is more parallel work and better amortization of memory movement.

Profiling & Debugging

Timing With CUDA Events

CUDA events measure elapsed GPU time between recorded events. This is appropriate for kernel timing, but it does not automatically include CPU work or memory allocation.

Reference: CUDA Runtime API event management.

Nsight Compute

Use Nsight Compute when you want kernel-level metrics: memory throughput, occupancy, warp stalls, branch behavior, and instruction mix. 

ncu --set basic .\build\01_vector_add.exe
ncu --set basic .\build\03_l2_distance_search.exe

Reference: Nsight Compute documentation.

Nsight Systems

Use Nsight Systems for whole-application timelines: CPU activity, CUDA API calls, kernel launches, copies, and overlap between compute and transfer.

Reference: Nsight Systems User Guide.

Compute Sanitizer

Use Compute Sanitizer to catch invalid memory access, race conditions, and sync bugs. It is slower than normal execution, but it is a wonderful bug net. 

compute-sanitizer .\build\01_vector_add.exe
compute-sanitizer --tool racecheck .\build\02_dot_product_reduction.exe

Reference: Compute Sanitizer documentation.

A practical optimization loop: verify correctness, measure baseline, profile bottleneck, change one thing, remeasure, document result. Small disciplined loops beat heroic guessing.

Vector Search Path

The current L2 kernel is an exact brute-force baseline. That baseline matters because ANN systems are only meaningful when you know what exact results and exact costs look like.

Exact Search

Computes distance from query to every vector. Simple, accurate, bandwidth-heavy. In Faiss vocabulary, this is like IndexFlatL2.

Read: Faiss guidelines to choose an index.

ANN Search

Avoids checking every vector. IVF clusters the search space, PQ compresses vectors, and graph methods like HNSW/CAGRA traverse neighbor graphs.

Read: NVIDIA cuVS documentation.

GPU Vector Search

GPU search depends heavily on batching, memory layout, candidate expansion, and keeping enough work on-device to amortize transfers.

Read: Fine-tuning GPU index algorithms.

Production Libraries

Study cuVS and Faiss after your baseline works. Then you can compare your code against real systems with humility and sharper eyes.

Repos: cuVS, Faiss, ANN-Benchmarks.

Interview Story

A strong Dnotitia-style story: "I implemented CUDA kernels from scratch, starting with bandwidth and reduction baselines, then used those ideas to build an exact L2 vector-search kernel. I measured kernel time with CUDA events, checked correctness against CPU references, and planned next steps for GPU top-k and batched search. My optimization process is: correctness first, baseline second, profiling third, one controlled change at a time."

Questions you should be ready to answer

  • Why use a grid-stride loop instead of launching exactly one thread per element?
  • What is memory coalescing, and how would you detect poor coalescing?
  • Why can the GPU result differ slightly from the CPU result in a reduction?
  • How would you separate kernel time from end-to-end latency?
  • Why is brute-force exact kNN still useful when ANN algorithms exist?
  • What would you optimize next in the L2 search kernel?
